# Sample logs

## Generated samples (checked in)

`sample_clean.{ulg,bin,tlog}` and `sample_flawed.{ulg,bin,tlog}` are committed
here — six small (~200-350KB) files covering all three supported formats,
each with a "clean" flight (no findings, 100/A) and a "flawed" one (sustained
~1.1Hz roll/pitch oscillation, battery sag, a mid-flight satellite drop).

These are **not real flight recordings** — they're deterministically
generated by [`scripts/generate_sample_logs.py`](../../scripts/generate_sample_logs.py)
from a synthetic flight profile (fixed random seed, reproducible). What makes
them useful despite being synthetic: each one is written using that format's
*real* binary encoder —

- **`.ulg`** — hand-written using the exact framing pyulog's own writer
  produces (`pyulog.core.ULog._write_file_header` / `_write_format_messages`
  / `_write_data_section`), reverse-engineered from that source rather than
  guessed.
- **`.bin`** — hand-written using ArduPilot's real dataflash framing
  (`0xA3 0x95 <type>` + struct body, `FMT` message bootstrapping), matched
  against `pymavlink.DFReader`'s own `FORMAT_TO_STRUCT` table.
- **`.tlog`** — actual MAVLink packets, packed via pymavlink's own
  `MAVLink.pack()` encoder (not hand-rolled), with the standard 8-byte
  big-endian microsecond timestamp framing `mavutil.mavlogfile` itself
  writes.

So `tests/test_sample_logs.py` runs all six through the **real** `pyulog`,
`pymavlink.DFReader`, and `pymavlink.mavutil` parsing code — not the mocked
readers the rest of the parser unit tests use — and asserts on realistic
findings (the flawed samples should trip oscillation/GPS findings; the clean
ones shouldn't trip anything). This is a meaningfully stronger guarantee than
unit tests alone: it proves the binary format handling itself is correct,
not just the field-mapping logic layered on top of it.

Regenerate with:

```bash
python scripts/generate_sample_logs.py
```

## What this doesn't replace

These synthetic samples can't catch firmware-version-specific field name
drift or unit-conversion mistakes the way a genuine recorded flight can —
they only exercise the field names and layouts this codebase itself assumes.
The ArduPilot parser has been separately validated by hand against a real
~220MB ArduCopter V4.3.5 dataflash log from an actual flight (this is what
caught the `vehicle_type` bug fixed in `ardupilot_parser.py` — the field was
always `None` until that test surfaced it); the PX4 ULog and MAVLink tlog
parsers have not yet had the same real-hardware pass.

If you have a real log and want to help close that gap:

- **PX4 ULog (.ulg)** — https://review.px4.io has downloadable sample logs,
  or fly a PX4 vehicle in SITL (`make px4_sitl gazebo`).
- **ArduPilot dataflash (.bin)** — Mission Planner's log download, or
  ArduPilot's SITL (`sim_vehicle.py`).
- **MAVLink telemetry (.tlog)** — QGroundControl / Mission Planner both write
  one automatically during any GCS-connected flight (simulated or real).

Drop it in this directory (it's gitignored except for the `sample_*` files
above) and run the parser directly, e.g.:

```python
from flightmd_core.services.ardupilot_parser import ArduPilotBinParser
topics, params, meta = ArduPilotBinParser().parse("tests/sample_logs/your_real_log.bin")
```

then compare a few findings against what Mission Planner / QGroundControl /
Flight Review shows for the same flight. The EKF analyser is intentionally
not wired up for ArduPilot/MAVLink yet (see `ardupilot_parser.py` and
`mavlink_telemetry_parser.py` docstrings) — that bit-flag mapping needs
real-log verification before it's safe to add.
